The Work

Three applications,
one coherent system.

Each layer introduced a new class of problem — and architectural decisions that compound across the stack.

01 · Data Platform · Weeks 1–2
Vinyl Collection App
A local-first data platform for managing, enriching, and analyzing a personal vinyl record collection. Evolved from CSV to a fully normalized, SQL-driven system with external API pipelines and AI overlays.
Python Streamlit SQLite SQL Discogs API OpenAI API
Collection dashboard — 339 albums, analytics, album of the day
Architectural decisions
CSV → SQLite
Persistent state, SQL-driven querying, eliminates full dataset reloads into memory
Canonical mapping tables
Normalized artists, genres, labels while preserving raw values — standard production data pattern
SQL as features
Top artists, decade distribution, label analytics are queries — not application logic
AI as non-critical overlay
OpenAI grades and summaries layer on top; core system is fully deterministic without them
Discogs enrichment pipeline
Batch backfill with rate limiting, error handling, and partial update logic — a real ingestion pattern
What this layer established
Structured, queryable data as the foundation for everything downstream. The quality of the data model here directly constrained what was possible in retrieval and ranking later.
Architecture pattern
UI → Service layer → Repository layer → SQLite. Clear separation that made the system extensible — adding the enrichment pipeline didn't touch the UI, and adding analytics didn't touch the API layer.
02 · AI Decision System · Weeks 3–4
Pressing Scout
An AI-assisted system for identifying exact vinyl pressings from photos. Combines vision-based evidence extraction, multi-hypothesis search generation, Discogs candidate retrieval, deterministic ranking, and human-in-the-loop confirmation into a single decision workflow.
React (Lovable) FastAPI · Python PostgreSQL OpenAI Vision Discogs API Pydantic · SQLModel
Landing — "Know Your Pressing Before You Buy"
AI evidence extraction — 70% confidence, structured JSON output
Photo submission — front jacket, back jacket, labels, deadwax
Ranked candidates — score 90, match reason, "Select this match"
System design
Not a classifier. A multi-stage decision pipeline: vision extraction → hypothesis generation → candidate retrieval → deterministic ranking → human confirmation. Each stage is independently debuggable.
Key boundary
OpenAI extracts and interprets noisy visual signals. Application code owns ranking logic, persistence, and all final state transitions. AI outputs treated as probabilistic inputs throughout.
Retrieval vs. ranking
A bad result can happen because the correct candidate was never retrieved — or because it was retrieved but ranked too low. These are different failure modes requiring different fixes and different metrics.
03 · Evaluation + Optimization · Week 5
Pressing Scout Workbench
An internal evaluation and optimization system. Establishes a golden dataset, runs configurable ranking evaluations, compares experimental runs against baseline, attributes failure patterns, and automates configuration search across hundreds of parameter permutations.
Python Streamlit MRR · Top-K · Recall@K Run-based eval Config search Failure attribution
Guided experiments — active baseline, experiment type selection
Signal weight tuning — 20+ configurable parameters, baseline vs. candidate
What Workbench does
Takes raw ranking outputs and converts them into quantified metrics, diagnosed failure patterns, and clear decisions: Verdict → Why → What next. Evaluation as a first-class system, not a reporting layer.
The optimization result
Hundreds of parameter configurations evaluated. No configuration outperformed baseline. The system could prove this — which itself is a high-confidence result. Redirected focus toward signal quality and retrieval rather than continued tuning.
What the system surfaced

Principles that emerged
from building it.

Not derived from reading about these systems — learned through debugging regressions, hitting architectural walls, and making real tradeoffs under uncertainty.

01
Separation of concerns is foundational, not stylistic
UI vs. logic vs. data. Retrieval vs. ranking. Deterministic vs. probabilistic. Every meaningful debugging session traced back to a boundary that hadn't been drawn clearly enough.
02
AI is strong at ambiguity. Weak at determinism.
OpenAI is excellent at interpreting noisy visual signals and reasoning under uncertainty. It cannot reliably own deterministic correctness, persistence logic, or final state. The boundary matters.
03
Data quality beats algorithm sophistication
The hardest matching failures required better input evidence — sharper label photos, clearer deadwax — not more complex ranking weights. Signal quality is the highest-leverage variable.
04
Intermediate state is a first-class asset
Candidate pools, extraction outputs, and user confirmations must be stored. Without persisted intermediate state, there's nothing to evaluate, debug, or optimize against.
05
Manual optimization fails at scale
Parameter interactions become non-linear faster than intuition can track. The right model: machine explores the configuration space, human interprets outcomes and makes decisions.
06
"No improvement" is a result, not a failure
Running hundreds of configurations and finding none that beats baseline is high-confidence signal. It tells you where not to invest effort — which is as valuable as finding what works.
